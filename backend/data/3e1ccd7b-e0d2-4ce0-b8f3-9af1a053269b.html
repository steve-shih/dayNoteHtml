RESTful API vs GraphQL：系統設計決策教材

用白話、圖解、決策樹與 Node.js 範例，理解兩種 API 設計方式的差異：什麼時候用 RESTful API，什麼時候用 GraphQL。

一、各自介紹

RESTful API

RESTful API 是把系統資料設計成一個一個「資源 Resource」，例如 /users、/orders、/products。前端透過 HTTP 方法操作資源。

GET 查詢POST 新增PUT/PATCH 修改DELETE 刪除

白話：像去餐廳點固定菜單。你要會員資料，就點「會員 API」；你要訂單資料，就再點「訂單 API」。

解決問題：讓前後端用標準 HTTP 規則溝通，簡單、清楚、好快取、好除錯。

GraphQL

GraphQL 是一種查詢語言與 API Runtime。前端可以自己指定「我要哪些欄位」，通常只打一個 endpoint，例如 /graphql。

Query 查詢Mutation 修改Schema 型別定義Resolver 資料解析

白話：像自助餐。你不是點固定套餐，而是自己夾「只要姓名、頭像、最近三筆訂單」。

解決問題：減少前端多次請求、避免資料拿太多或太少，適合資料關聯複雜、多端需求不同的系統。

二、畫圖介紹

RESTful API：多個資源 endpoint

重點：REST 的思考是「每個資源都有自己的門」。清楚，但頁面若要很多關聯資料，可能需要打多個 API。

GraphQL：單一入口，自訂欄位

重點：GraphQL 的思考是「前端描述要什麼，後端幫你組出來」。彈性高，但後端 Schema、Resolver、效能控管要設計好。

四、優缺點比較

面向RESTful APIGraphQL
核心概念以資源 endpoint 為中心。以 Schema 與 Query 為中心。
學習成本低，HTTP 觀念直覺。中高，需要理解 Schema、Resolver、N+1、Query Complexity。
前端彈性較低，endpoint 回什麼通常後端決定。高，前端可指定欄位。
資料過多/過少容易 over-fetching / under-fetching。較能避免，因為可指定欄位。
快取天然支援 HTTP Cache、CDN、ETag。較複雜，通常需要 Apollo/Client Cache 或自訂策略。
除錯與監控URL、Status Code、Log 很直觀。所有請求常進 /graphql，需要額外記錄 operation name 與 query cost。
權限控管可依 endpoint 控制。需到 field/resolver 層級設計權限。
效能風險多次請求、資料重複傳輸。查詢過深、N+1、複雜 query 可能拖垮後端。
適合情境CRUD、外部 API、穩定資源、公開服務。複雜資料關聯、多端需求不同、前端快速變動。

五、基本使用方法

RESTful API 基本設計

Client→GET /users/1→Controller→DB
// RESTful API：Express 範例
import express from 'express';

const application = express();
application.use(express.json());

const users = [
  { id: 1, name: 'Steve', email: 'steve@example.com' }
];

// STEP_01：查詢單一會員資料
application.get('/users/:userId', (request, response) => {
  const userId = Number(request.params.userId);
  const user = users.find((userItem) => userItem.id === userId);

  if (!user) {
    return response.status(404).json({ message: '找不到會員' });
  }

  return response.status(200).json(user);
});

// STEP_02：新增會員資料
application.post('/users', (request, response) => {
  const newUser = {
    id: users.length + 1,
    name: request.body.name,
    email: request.body.email
  };

  users.push(newUser);
  return response.status(201).json(newUser);
});

application.listen(3000);

GraphQL 基本設計

Client→Query 欄位→Resolver→DB
// GraphQL：Apollo Server 範例
import { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';

const users = [
  { id: '1', name: 'Steve', email: 'steve@example.com' }
];

// STEP_01：定義前端可以查什麼資料型別
const typeDefinitions = `#graphql
  type User {
    id: ID!
    name: String!
    email: String!
  }

  type Query {
    user(userId: ID!): User
    users: [User!]!
  }
`;

// STEP_02：定義每個欄位實際怎麼取得資料
const resolvers = {
  Query: {
    user: (_, argumentsObject) => {
      return users.find((userItem) => userItem.id === argumentsObject.userId);
    },
    users: () => users
  }
};

const server = new ApolloServer({
  typeDefs: typeDefinitions,
  resolvers
});

await startStandaloneServer(server, {
  listen: { port: 4000 }
});

GraphQL Query 長這樣

query GetUser {
  user(userId: "1") {
    id
    name
  }
}

這個 query 只會要求 id 與 name，不會拿 email。這就是 GraphQL 的核心優勢之一。

實務建議

如果你是從 Node.js 後端開始練習，我建議順序是：

  1. 先用 Express 做 RESTful API，理解 route、controller、service、status code。
  2. 再用 Swagger/OpenAPI 產生 API 文件。
  3. 遇到多端欄位需求不同、頁面要組合大量關聯資料時，再練 Apollo GraphQL。
  4. GraphQL 上線前一定要補：權限、query depth limit、query complexity、DataLoader、operation log。

七、總結：怎麼選最快？

選 RESTful API

需求穩定、CRUD 明確、外部串接多、想簡單快取與除錯。

選 GraphQL

資料關聯複雜、多端欄位不同、前端變動很快、想減少多次請求。

混合使用

大多數系統可以 REST 為主，複雜查詢頁面用 GraphQL 或 BFF 聚合 API。

一句話：RESTful API 是「後端設計好固定資源菜單」；GraphQL 是「前端自己描述要哪些資料」。小到中型 CRUD 系統先 REST；多端、多欄位、多關聯的大型前端系統再考慮 GraphQL。
