一、DevOps Dashboard 的核心目的

Dashboard 不是把所有數字塞上去，而是用來回答：「現在有沒有壞？壞在哪裡？影響誰？要先救哪裡？」

1. SLI / SLO / SLA

SLI 是服務指標，例如成功率、延遲。
SLO 是內部目標，例如 99.9% 可用性。
SLA 是對客戶承諾，違反可能賠償。

AvailabilityLatencyError Rate

2. Golden Signals

Google SRE 常用四大訊號：Latency 延遲、Traffic 流量、Errors 錯誤、Saturation 飽和度。

3. RED / USE 方法

RED 看服務：Rate、Errors、Duration。
USE 看資源：Utilization、Saturation、Errors。

APIInfraDBK8s
實務建議：第一層 Dashboard 看「使用者體感」，第二層才看「系統資源」。不要一開始就只看 CPU，因為 CPU 高不一定代表服務壞。

四、告警設定原則

不要只用單點閾值

例如 CPU 超過 80% 立刻告警，容易誤報。較好的方式是：CPU > 80% 持續 10 分鐘，並搭配 API 延遲或錯誤率。

分級：Info / Warning / Critical

Info：只記錄。
Warning：需要觀察。
Critical：會影響客戶，需要即時處理。

先看「影響使用者」

核心告警建議優先用：5xx、P95/P99 latency、成功率、付款/登入/查詢等核心流程失敗率。

用基準線做動態判斷

像流量、4xx、成本這類數字會隨時間變化，建議用歷史平均、尖峰時段、週期比較，而不是固定死門檻。

五、建議 Dashboard 分頁設計

Page 1：Executive Overview

給主管與值班快速看：服務可用率、錯誤率、核心 API 延遲、目前 Incident、部署版本。

Page 2：Service / API

每個 API 的 RPS、P95、P99、5xx、4xx、Timeout、Top Slow Endpoint。

Page 3：Infrastructure

CPU、Memory、Disk、IO Wait、Network、Load Average、Process 狀態。

Page 4：Database

連線數、慢查詢、鎖等待、讀寫量、索引命中率、Replica Lag。

Page 5：Kubernetes

Pod 狀態、Restart、Pending、Node 壓力、HPA、CPU/Memory Request 與 Limit。

Page 6：CI/CD

部署成功率、部署時間、Rollback 次數、測試失敗率、版本與 Commit 對應。

Page 7：Security

登入失敗、異常 IP、權限拒絕、WAF、Token 錯誤、敏感 API 呼叫。

Page 8：Cost

每日成本、VM/DB/Storage/Network 成本、閒置資源、成本異常。

六、故障處理 Runbook：實務排查順序

STEP_01：確認影響範圍

是全部服務壞？單一 API 壞？單一區域壞？只有部分客戶壞？先決定事件等級。

STEP_02：看 Golden Signals

先看 Traffic、Error、Latency、Saturation。不要一開始只看 log，容易迷路。

STEP_03：對照部署時間

如果錯誤開始時間與部署時間吻合，優先 rollback 或切回穩定版本。

STEP_04：找瓶頸層

API 慢 → DB 慢？Queue 堆？CPU/Memory/IO 飽和？外部服務 timeout？逐層排除。

STEP_05：先止血

擴容、限流、關閉非核心功能、清理磁碟、重啟異常 Pod、Rollback。

STEP_06：RCA 與補防線

事件後補：告警、Dashboard、壓測、部署檢查、自動回滾、容量規劃。

面試或實務回答模板

我會先從使用者體感指標判斷服務是否真的受影響，例如 5xx、P95/P99 延遲與成功率。確認影響範圍後，再往下分流到流量、資源、DB、Queue、Kubernetes 與近期部署紀錄。若是核心服務異常，優先止血，例如 rollback、擴容、限流或暫停非核心任務；事後再做 RCA，補上監控與自動化防線。
