怎麼讀這份工具箱？

不要死背名詞。設計系統時，先問：「我現在痛的是哪裡？」是物件建立很亂？業務規則很複雜？部署擴充困難？還是測試驗證不足？不同問題對應不同工具。

Design Pattern
解決局部程式碼變化點。
DDD / 架構模式
解決業務複雜度與系統邊界。
TDD / BDD / SDD
解決怎麼確認做對、怎麼協作。

一、設計原則 Principles

原則不是 Pattern，而是判斷程式碼是否健康的標準。

SOLID
物件導向設計的五大原則
Principle
解決什麼問題：類別太肥、依賴太硬、改一個地方壞一堆。
白話例子：訂單系統中，OrderService 不應同時負責折扣、寄信、付款、產生 PDF。每件事應有清楚職責。
常見導向：SRP 拆職責、OCP 用 Strategy/Factory、DIP 用 Interface + DI。
S：單一職責
O：開放擴充，關閉修改
L：子類可替代父類
I：介面小而專一
D：依賴抽象，不依賴具體
DRY / KISS / YAGNI / 關注點分離
讓系統不要過度重複、過度複雜、過度設計
Principle
解決什麼問題：同一段規則散落各處、架構太華麗但需求根本用不到。
白話例子：只有 3 個 CRUD API，不需要一開始就拆微服務、CQRS、Event Sourcing。
判斷：重複兩次先觀察，重複三次再抽象；看得懂比炫技重要。

二、Design Patterns 設計模式

Design Pattern 是針對「常見程式設計問題」的經典解法，不是架構全餐。

Creational Patterns 建立型模式
專門處理物件怎麼建立
Design Pattern
解決什麼問題：到處 new、建立條件很多、建立步驟複雜。
白話例子：依照付款方式建立 CreditCardPayment、LinePayPayment、ApplePayPayment。
包含：Factory Method、Abstract Factory、Builder、Prototype、Singleton。

→

→

Factory Method
把 new 的判斷集中到工廠方法
Creational
解決：呼叫端不想知道要 new 哪個類別。
例子：輸入 paymentType = credit_card，就建立信用卡付款物件。
適合：同一類型物件有多種實作。

Abstract Factory
建立一整組互相搭配的物件家族
Creational
解決：多個物件必須成套搭配，不能混用。
例子：Windows UI 產生 WindowsButton + WindowsInput；Mac UI 產生 MacButton + MacInput。
適合：主題切換、跨平台元件、品牌套件。

例子：建立報表：設定日期、欄位、排序、群組、匯出格式。

Structural Patterns 結構型模式
專門處理物件之間怎麼組合、包裝、隔離
Design Pattern
解決：介面不合、系統太複雜、想加功能但不想改原類別。
白話例子：舊金流 API 和新系統格式不同，用 Adapter 包起來。
包含：Adapter、Facade、Decorator、Proxy、Composite、Bridge、Flyweight。

Adapter：轉換不相容介面，像轉接頭。
Facade：把複雜子系統包成簡單入口，像客服櫃台。
Decorator：不改原物件，外面一層層加功能，像飲料加珍珠、奶蓋。
Proxy：代理控制存取、快取、權限，像秘書擋不必要請求。

Behavioral Patterns 行為型模式
專門處理流程、演算法、狀態、通知、任務
Design Pattern
解決：if/else 很多、狀態切換複雜、物件互相通知混亂。
白話例子：不同會員等級有不同折扣，用 Strategy 切換折扣演算法。
包含：Strategy、Observer、State、Command、Chain、Template Method 等。

Strategy / Observer / State / Command 等
行為型常用模式速查
Behavioral
Strategy：演算法可替換，例如折扣策略。
Observer：一對多通知，例如訂單付款成功後通知庫存、物流、寄信。
State：狀態不同，行為不同，例如訂單待付款/已付款/取消。
Command：把操作包成任務，例如排程、Undo、重試。
Chain：多關卡依序處理，例如權限檢查、資料驗證、風控。

三、架構模式 Architecture Patterns

架構模式是系統骨架，處理模組邊界、依賴方向、部署與資料流。

MVC / Layered / Clean / Hexagonal
常見單體或模組化系統骨架
Architecture
解決：畫面、業務邏輯、資料庫混在一起。
例子：Controller 接 API，Service 處理業務，Repository 存取 DB。
選擇：簡單 CRUD 用 MVC/Layered；業務複雜用 Clean/Hexagonal。
Controller / UI
Application Service
Domain Model
Repository / Infrastructure
CQRS / Event-Driven / Microservices / BFF
大型系統與多服務協作常見架構
Architecture
解決：讀寫負載差異大、多系統要非同步協作、不同前端需要不同 API。
例子：訂單成立後發事件，庫存服務、物流服務、通知服務各自處理。
注意：不要一開始就微服務。先確認團隊、部署、資料一致性是否真的需要。

四、領域設計與分析方法

當業務規則比 CRUD 複雜時，需要先把業務語言、邊界和規則整理清楚。

DDD：Domain-Driven Design
用業務模型驅動系統設計
Domain
解決：業務規則散落程式、工程師和業務講不同語言、模組邊界不清楚。
例子：長照系統的個案、排班、打卡、補助、核銷，不只是資料表，而是有規則的領域模型。
核心名詞：Bounded Context、Entity、Value Object、Aggregate、Repository、Domain Service。

用事件把業務流程攤開來討論

例子：訂單已建立 → 付款成功 → 庫存已扣除 → 物流已建立 → 通知已寄出。
適合：開發前釐清流程、找出邊界、找出事件與命令。

五、開發流程與測試方法

這類方法不是架構，而是讓需求、規格、測試、程式碼能對齊。

TDD / BDD / ATDD / SDD
從測試、行為或規格推動開發
Process
解決：寫完才發現需求誤解、改程式不敢動、測試不足。
白話：TDD 先寫測試；BDD 用 Given-When-Then 描述行為；ATDD 先定驗收條件；SDD 先寫規格再生成/實作。
適合：核心業務規則、複雜流程、高風險功能。

六、系統整合與分散式設計

當系統開始跨服務、跨隊伍、跨資料庫，就會遇到可靠性與一致性問題。

Queue / Outbox / Retry / Circuit Breaker / Idempotency
讓分散式系統更可靠
Distributed
解決：API 失敗、重複請求、服務互相拖垮、事件漏送。
例子：付款成功後寫入 Outbox，再由背景工作送事件，避免 DB 成功但事件沒送出去。
常用：Retry 處理暫時失敗；Circuit Breaker 防止連鎖故障；Idempotency 防重複扣款。

七、資料庫與資料設計模式

資料設計不只建表，還包含查詢模型、歷史紀錄、一致性與效能。

ER / 正規化 / Index / Audit Log / Sharding
資料結構、效能、歷史與擴展
Data
解決：資料重複、查詢慢、歷史追蹤不清楚、資料量變大。
例子：重要表加 Audit Log 記錄誰在什麼時間改了什麼；大量資料用 Partition 分區。
判斷：交易資料重一致性；報表資料重查詢速度。

八、UI / 前端設計模式

前端也需要架構，尤其是狀態、元件、資料流與設計系統。

Component / Redux / Hooks / Atomic Design / Design System
前端元件與狀態管理
Frontend
解決：畫面邏輯重複、狀態混亂、UI 不一致。
例子：把按鈕、表單、Modal 做成共用元件；複雜流程用狀態機控制。
適合：React/Vue/Angular 專案、後台系統、設計系統。

最後總結：選工具前先問問題

  • 物件建立很亂 → 先看 Creational Pattern。
  • 介面不合、包裝複雜 → 先看 Structural Pattern。
  • 流程、狀態、通知、演算法很多 → 先看 Behavioral Pattern。
  • 業務規則複雜 → 先看 DDD / Event Storming。
  • 依賴方向混亂 → 先看 Clean Architecture / Hexagonal。
  • 讀寫差異大、多服務協作 → 先看 CQRS / Event-Driven。
  • 不敢改程式 → 先補 TDD / BDD / CI/CD。
老大記憶法：Pattern 是局部招式，Architecture 是骨架，DDD 是業務地圖，TDD/BDD/SDD 是驗證方法，分散式模式是大型系統的保命機制。
