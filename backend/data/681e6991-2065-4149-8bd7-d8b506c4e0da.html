GCP 自動升規、壓力測試與防爆費用測試計劃

目標：驗證網站或 API 在流量上升時能自動水平擴充、健康檢查自動替換壞機、更新時分台滾動重啟，同時用 Cloud Armor 與費用上限避免壓測造成爆量費用。

一、測試總目標

效能目標

壓測RPSP95 延遲

確認服務在正常流量、尖峰流量、異常流量下都能維持可接受的回應速度。

升規目標

MIGAutoscalingRolling Update

驗證 Managed Instance Group 會依 CPU 或 HTTP 負載自動增加 VM，並能一台一台更新。

防守目標

Cloud ArmorRate LimitBudget Alert

避免同 IP 惡意或誤操作壓測打爆服務，也避免自動升規造成大量費用。

三、升規策略設計

策略建議設定原因
水平擴充 Horizontal Scalingmin=2、max=5、CPU target=60%~70%正式環境優先用多台 VM 分散風險，max 必須設定，避免費用無限上升。
垂直擴充 Vertical Scaling不做即時自動升級，改用新 Instance Template + Rolling UpdateVM 規格變更通常涉及重建或替換，不適合當成即時防線。
AutohealingHealth Check: /health服務異常時，MIG 可自動重建 VM。
Rolling Updatemax unavailable=1、max surge=1更新時一次只動一台，保留服務可用性。

四、壓力測試階段規劃

Phase 1：基準測試 Baseline Test

目的：確認單台或最低兩台 VM 的正常承載能力。

hey -z 5m -c 20 https://your-domain.com/api/health
  • 觀察 RPS、平均延遲、P95 延遲、錯誤率。
  • Cloud Monitoring 觀察 CPU、Memory、Network、LB request count。
  • 此階段不應觸發 autoscaling。

Phase 2：漸進式升壓 Ramp-up Test

目的：逐步提高併發，觀察何時觸發自動擴充。

hey -z 10m -c 50 https://your-domain.com/api/search
hey -z 10m -c 100 https://your-domain.com/api/search
hey -z 10m -c 200 https://your-domain.com/api/search
  • 確認 CPU 超過 60%~70% 後，MIG 是否新增 VM。
  • 確認新 VM 進入 healthy 狀態後，Load Balancer 才開始導流。
  • 記錄 scale out 所需時間。

Phase 3：尖峰流量 Spike Test

目的：模擬短時間暴增流量，測試系統保護能力。

hey -z 3m -c 500 https://your-domain.com/api/search
  • 確認系統不會直接全部 timeout。
  • 確認 Cloud Armor 是否對異常同 IP 請求限流。
  • 確認 MIG 不超過 max instances。

Phase 4：防守測試 Defense Test

目的：模擬同 IP 多次攻擊或誤操作壓測。

hey -z 5m -c 1000 https://your-domain.com/api/heavy
  • 同 IP 超過門檻時，Cloud Armor 應 throttle 或 deny。
  • 後端 VM CPU 不應因單一來源流量長時間滿載。
  • 錯誤碼可接受為 429 或 403。

Phase 5：故障與滾動重啟測試 Failure / Rolling Restart

目的：驗證一台 VM 壞掉或更新時，服務不中斷。

# 模擬單台 VM App 掛掉
sudo systemctl stop docker

# 或更新 Instance Template 後執行 rolling update
  • Load Balancer 應停止導流到 unhealthy VM。
  • MIG 應自動修復或重建 VM。
  • Rolling Update 過程中錯誤率應維持在可接受範圍。

五、Cloud Armor 防守規則建議

規則建議值處理方式
測試 IP 白名單公司 IP / 自己 VPN IP允許較高測試量，避免誤封自己。
一般 IP Rate Limit每分鐘 300 request超過先 throttle。
高風險 IP 封鎖每分鐘 1000 request短時間 deny，例如 10 分鐘。
高成本 API 保護/api/heavy、/api/export更低門檻，避免資料庫或報表功能被打爆。
非測試期間壓測入口/api/load-test非測試時間直接封鎖。

六、費用防爆設計

必要限制

  • MIG max instances：例如最多 5 台，禁止無限開機。
  • Budget Alert：50%、80%、100% 發通知。
  • Quota：不要把 VM、外部 IP、Load Balancer quota 開太高。
  • 壓測時間：每次壓測 3~10 分鐘，避免長時間忘記關。

測試停止條件

  • 錯誤率超過 5%。
  • P95 延遲超過 2 秒並持續 3 分鐘。
  • MIG 已達 max instances。
  • Cloud Billing 快速增加或收到預算警示。
  • 資料庫 CPU 或連線數接近上限。

八、正式測試清單

  • 確認 /health 不依賴資料庫重查，避免健康檢查本身造成壓力。
  • 確認 Load Balancer backend health check 已通過。
  • 確認 MIG 設定 min / max instance，尤其 max 不可省略。
  • 確認 Cloud Armor 已掛到 Backend Service。
  • 確認 Billing Budget Alert 已建立。
  • 確認 Cloud Monitoring Dashboard 可看到 CPU、RPS、延遲、錯誤率。
  • 確認壓測工具不在正式 App VM 上執行。
  • 壓測後輸出報告：最大 RPS、P95、錯誤率、最高開幾台 VM、是否觸發封鎖。

九、建議指令範例

hey 壓測

brew install hey

# 基準測試
hey -z 5m -c 20 https://your-domain.com/api/health

# 升壓測試
hey -z 10m -c 100 https://your-domain.com/api/search

# 尖峰測試
hey -z 3m -c 500 https://your-domain.com/api/search

k6 壓測腳本

import http from 'k6/http';
import { sleep, check } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 50 },
    { duration: '5m', target: 100 },
    { duration: '2m', target: 0 },
  ],
  thresholds: {
    http_req_failed: ['rate<0.03'],
    http_req_duration: ['p(95)<2000'],
  },
};

export default function () {
  const response = http.get('https://your-domain.com/api/search');
  check(response, { 'status is 200': (result) => result.status === 200 });
  sleep(1);
}
